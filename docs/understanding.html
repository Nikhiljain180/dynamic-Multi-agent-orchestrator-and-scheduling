Documentation of My Understanding

How I interpreted the problem, mapped requirements to code, and why I chose LangGraph, Telegram, and a three-layer architecture for agent orchestration.

Problem Requirements Architecture Flows Data model Tradeoffs Codebase

1 Problem understanding

The challenge asks for a platform, not a single chatbot. Users must be able to define agents, compose workflows, execute on a real runtime, observe runs, and interact via an external channel — all from a web UI.

🤖

Configure agents

Personality, tools, memory, skills, guardrails, provider overrides

🔀

Compose workflows

Linear pipelines, conditional routing, feedback loops

⚡

Real runtime

LangGraph executes LLM calls and tools — not a UI mock

📡

Observe & converse

Live monitor, message history, Telegram integration

Core insight: separation of concerns — configuration (agents), composition (workflows), execution (LangGraph), persistence (Postgres), and real-time observation (Redis + WebSocket) are distinct layers that must stay in sync.

Why LangGraph?

LangGraph ✓ chosen

Explicit graphs, conditional edges, feedback loops — maps to React Flow canvas

CrewAI

Faster role-based setup; less control over custom branching

AutoGen

Conversational multi-agent; harder to visualize structure

Why Telegram?

Free Bot API, works locally with polling (no webhook tunnel), reliable for demos. The adapter pattern isolates channel logic — Slack/WhatsApp can follow the same receive → run → reply contract.

Other key decisions

  • Graph repair on backend — graph_repair.py + /api/workflows/repair-graph keeps routing rules in one place
  • Guardrails in runtime — token caps and tool allowlists enforced in _apply_guardrails(), not only UI
  • Honest LLM failures — no silent mock fallback during demo runs (ALLOW_MOCK_LLM_FALLBACK=false)

Scheduled runs

Cron + run input saved on workflow → background scheduler (UTC) → run with channel: schedule → managed from Schedules tab (pause / resume / delete).
